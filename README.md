## 1. Executive Summary & The Core Thesis

Given an **arbitrary area (polygon/bbox)** and a **flood date**, TRISHUL answers three critical operational questions for rescue teams in steep Himalayan terrain:

1. **Where did the flood hit?** (Prong 1: Hazard) — Calibrated water, debris deposit, and channel scour footprints from Sentinel-1 SAR and Sentinel-2 optical imagery.
2. **What was damaged?** (Prong 2: Exposure) — Pre-event OpenStreetMap buildings, roads, and bridges with probabilistic damage scores ($p_{\text{hit}}$).
3. **Who is cut off?** (Prong 3: Isolation) — Settlements isolated from hospitals and supply hubs evaluated via spatially correlated Monte-Carlo network percolation, accompanied by a greedy restore-first repair schedule.

### Why Standard Methods Fail in the Himalaya (and Why TRISHUL Wins)
Conventional flood mapping thresholds a single SAR log-ratio and overlays it with OSM. In the Himalaya, this fails because:
- **Radar layover and shadow** produce false water detections. *TRISHUL introduces a 3D ray-marched terrain-geometry gate and multi-track fusion (ascending + descending).*
- **Debris floods, not clean water:** Events like the August 2026 Trishuli flood deposit rocky slurry with high radar backscatter. *TRISHUL introduces EVENT-ADAPT optical-to-SAR cross-teaching.*
- **Sub-pixel bridges:** 10 m pixels cannot resolve bridges. *TRISHUL introduces a physical noisy-OR model evaluating hydraulic flood-stage vs deck clearance and bank approach scouring.*
- **Uncertainty loss:** Thresholding discards confidence. *TRISHUL propagates calibrated probabilities from radar pixels to road graphs via 200 Monte-Carlo percolation draws.*
- **Monsoon cloud cover:** *TRISHUL operates gracefully in SAR-only mode, publishing an honest Blindspot Map.*

## 3. System Architecture

```
            ┌────────────── INGEST + COMPLIANCE FIREWALL (§2.2) ───────────────┐
            │ CDSE S1/S2 · Copernicus DEM · ohsome OSM snapshot · host allowlist │
            └───────┬───────────────┬───────────────────┬──────────────┬───────┘
                    ▼               ▼                   ▼              ▼
          SAR GEOMETRY GATE   OPTICAL EVIDENCE     TERRAIN LAYER    OSM ASSETS
          (shadow/layover,    (NDVI/BSI/NDWI,      (HAND, flow      (buildings,
           local incidence,    cloud/snow gates)    paths, slopes)   roads, bridges)
           per-track r_geo)         │                   │               │
                    ▼               │                   │               │
          TEMPORAL-STATS CHANGE     │                   │               │
          (same-track stack,        │                   │               │
           calibrated p-values)     │                   │               │
                    ▼               ▼                   ▼               │
          ┌──────────── AI: Segmentation CNN (Kuro Siwo) ───────────┐    │
          │  + EVENT-ADAPT: optical→SAR cross-teaching for debris   │    │
          └──────────────────────────┬──────────────────────────────┘    │
                                     ▼                                   │
                  EVIDENCE FUSION (calibrated log-odds, reliability-     │
                  weighted, multi-track) ⇄ HYDRAULIC CONSISTENCY LAYER   │
                  (flood-stage profile along thalweg, HAND prior)        │
                                     ▼                                   │
        ┌───────────── PRONG 1: HAZARD  (Where did it hit?) ─────────────┤
        │  hazard_prob (water/debris/scour/slope-failure), blindspot map │
        ├───────────── PRONG 2: EXPOSURE (What was damaged?) ◄───────────┘
        │  per-asset p_hit with CI; bridge model (sub-pixel)
        ├───────────── PRONG 3: ISOLATION (Who is cut off?)
        │  Monte-Carlo road-graph survival → P(cut-off), repair priority
        └──────────────► CLAIM LEDGER → EN/NE report · Dashboard · Q&A
```

## 4. Quickstart & Reproducibility

### Prerequisites
- Python 3.12+ and `uv` (recommended) or standard `pip`
- Docker (optional, for containerized run)

### Local Setup
```bash
# 1. Clone repository
git clone https://github.com/HirthikBalaji/trishul.git
cd trishul

# 2. Install dependencies (creates .venv with all requirements)
make setup

# 3. Run full automated test suite & compliance firewall
make test
make lint
make firewall
```

### Running the Trishuli August 2026 Case Study
```bash
# Executes end-to-end pipeline: Ingest -> Physics -> AI -> Exposure -> Isolation -> PDF Reports
make case-study
```

### Live "Judge Mode" on Any Unseen Himalayan Valley
```bash
# Execute on any arbitrary valley polygon and event date live
python -m trishul.pipeline \
  --aoi '{"type": "Polygon", "coordinates": [[[85.25, 28.10], [85.40, 28.10], [85.40, 28.25], [85.25, 28.25], [85.25, 28.10]]]}' \
  --event-date 2026-08-26 \
  --output runs/judge_run
```

### Launching the Web Dashboard & API
```bash
make api   # Starts FastAPI backend on http://localhost:8000
```
Open `http://localhost:8000` in any web browser to view the interactive MapLibre GL UI with swipe comparison, evidence drawers, flowpath traces, and bilingual Rescuer Copilot.

### Running via Docker
```bash
make docker-build
make docker-up
```

**Educational prototype, not an operational tool.**  
TRISHUL was built for the Multimodal AI Hackathon 2026. It is an experimental prototype and not an operational life-safety dispatch system. In solemn respect for the communities affected by recent disasters, no imagery of victims is used or displayed anywhere in this project.
